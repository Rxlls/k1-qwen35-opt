# 演示截图与指标对照说明

> 用途：答辩/评审时按顺序展示"做了什么、快多少、怎么证明"。
> 配套：`docs/技术文档.md`（完整数据与归因）、`docs/DEPLOY.md`（部署与排障）、`docs/PATCH_TCM.md`（TCM 改造）。

---

## 0. 这批图是什么（先看这一段）

**它们不是屏幕截图，是"实机原始输出重排版"。**

原因：K1 的 X 会话从 ssh 侧抓帧得到的是全黑图（`ffmpeg -f x11grab` 拍到的只有光标，桌面没有窗口管理器绘制任何东西），
拿不到可用的终端画面。因此改用另一条更可靠的路：

1. 通过 ssh 在 K1 上**真实执行**每一条命令；
2. 把 stdout 原样抓回；
3. 用统一模板渲染成 1440×810 的图，**数值、单位、措辞一律不改**，只做长行折行与省略号裁剪。

每张图底部都有「数据来源 + 时间」，表格类图另外标注「整理自 results/ 归档记录」与测量口径——
**看图的人可以逐条回到命令和记录去核对**。

如果评审要求"必须是现场屏幕截图"，用同一个命令在 K1 桌面的终端里重跑一次即可（见 §3），
画面要素与标注数字完全对应，不需要重新设计。

## 2. 逐图说明

### 图 1 · 环境与硬件身份

- **画面要点**：`riscv64` 出现在内核串里；ISA 串里 `_zve32x/_zve64d/_zvfh`（RVV）与结尾 `_ime` 同时存在。
- **标注**：8 核、7849 MB（可用 6986 MB）、Bianbu 2.3.5、Linux 6.6.63、NVMe 118 G。
- **图注**：*K1 实机：Bianbu 2.3.5 / 内核 6.6.63 / 8×X60，ISA 串中 RVV 与 IME 扩展同时在位——这是后续所有加速的前提。*
- **为什么先放这张**：后面所有数字都建立在"这台机器确实有 RVV 和 IME"之上；否则 +87.8% 无从解释。

### 图 2 · 一键部署自检

- **画面要点**：环境项逐条 `[OK]`；模型体积；冒烟那行 `推理正常出字` 与末尾 `通过 14 项，失败 0 项`。
- **标注**：14/14（环境 11 + 模型 2 + 冒烟 1）、2B 1265 MB、4B 2573 MB、冒烟 3.1 t/s。
- **图注**：*`deploy.sh` 从架构、扩展、内存、依赖包一路检到模型体积与冒烟推理，14 项全绿；脚本失败即停并给出修复建议。*

### 图 3 · 根因：量化类型是否在 IME 白名单内

- **画面要点**：两份"类型分布"行；官方那份含 `Q5_K / Q8_0 / Q6_K`，自产那份只有 `Q4_0`（外加 1 个 `Q8_0` 的 embedding）。
- **标注**：非白名单张量 **55 → 1**（Q5_K 18 + Q8_0 36 + Q6_K 1）；Q4_0 张量 129 → 186；体积 1.12 → 1.22 GiB。
- **图注**：*文件名都叫 Q4_0，实际类型分布完全不同：官方文件混入 55 个不在 IME 白名单的张量，整条 prefill 通路退化为通用实现。*
- **答辩提示**：这张图是"为什么快"的唯一解释，先看它再看性能表，因果链才闭合。

### 图 4 · 端到端出字

- **画面要点**：模型对中文提问的实际回复文本，无乱码、无重复。
- **标注**：2B 生成 2.7 t/s（`-n 260` 长输出实测，与 bench 的 2.80 一致）、4B 1.4 t/s（与 bench 的 1.43 一致）。
- **图注**：*同一台机器上的中文生成：词表、chat 模板、MTP 剥离后的张量布局全部正确。*
- **两处版式说明**（不影响结论）：
  1. 这个模型默认开启思考模式，`--chat-template-kwargs '{"enable_thinking":false}'` 与 `/no_think` 在本版运行时均未生效，
     完整输出是「思考过程 + 最终回复」；图中思考过程只保留前两段并标注"从略"，最终回复逐字未改。
  2. 回复原文含 1 个表情符号（😊），等宽终端字体无对应字形，图中略去。

### 图 5 / 图 6 · 官方 vs 自产（2B / 4B）

- **画面要点**：三行配置（官方 Q4_0 / 自产 Q4_0 / 自产 Q4_K_M）+ 条形图。
- **标注**：2B `pp512 10.84 → 20.36（+87.8%）`，decode `2.84 → 2.80`；4B `3.80 → 8.10（+113.2%）`，decode `1.32 → 1.43（+8.3%）`。
- **图注**：*同硬件、同运行时、同参数，只换权重文件：2B prefill 翻倍、4B prefill 翻倍且 decode 转正。decode 在 2B 上几乎不变，说明它受带宽约束，与量化类型无关。*
- **答辩提示**：被问"是不是调参调出来的"时，指这一行——变量只有量化类型一个。

### 图 7 · 长上下文下的优势保持

- **画面要点**：0 / 4096 / 8192 / 16384 四档深度，两版 pp512 与 tg64 成对出现。
- **标注**：`20.24 / 14.65 / 11.76 / 8.17`；优势 `+87.8% / +62.8% / +51.7% / +35.9%`；decode 保持率 `44.8% vs 45.8%`。
- **图注**：*优势随深度单调收窄但始终为正；decode 两版衰减曲线几乎重合——上下文衰减由注意力通路决定，与权重量化无关。*

### 图 8 · 负结果排除矩阵

- **画面要点**：四条被排除的路径及其实测数字、判定列。
- **标注**：v0.2.3 `7.99`（比 legacy 低 23%）；`-t 8` → `0.86`（−70%）；TCM patch `20.36 → 20.36`（Δ0）；KV q8_0 `31 min 未完成`（f16 仅 17.9 min）。
- **图注**：*四条直觉路径全部被实测排除，优化点因此收敛到单一变量：量化类型。*

## 3. 如果需要"真机屏幕截图"

在 K1 桌面上开一个终端（LXQt 的 qterminal），把上图对应的命令原样敲一遍即可。要点：

```bash
# 1) 先统一终端外观，保证多次截图一致
qterminal --workdir ~/cie

# 2) 逐条执行，命令与图里完全一致（见 §1 总表第 3 列）

# 3) 需要整屏取证时（K1 本机执行，不是在 ssh 里）
DISPLAY=:0 ffmpeg -y -f x11grab -video_size 1920x1080 -i :0.0 -frames:v 1 -update 1 shot.png
```

> 本机的 X 会话当前抓帧为全黑（无窗口管理器绘制），所以自动化取证走的是"输出重排版"这条路；
> 人工在桌面上操作时截图正常。

## 4. 生成方式（可复现）

```bash
python3 tools/make_shots.py          # 全部 8 张 → docs/figs/demo/
python3 tools/make_shots.py fig5     # 只重绘某一张
```

- 每张图的数据写在 `tools/make_shots.py` 的 `SHOTS` 列表里，与本节表格一一对应；
- 改数字只需改对应条目，**不要手改 PNG**；
- 终端类图（1/2/3/4）的文字必须是真实 stdout，表格类图（5/6/7/8）必须能在 `results/` 里找到原始记录。
