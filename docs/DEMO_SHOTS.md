# 演示截图与指标对照说明

> 用途：答辩/评审时按顺序展示"做了什么、快多少、怎么证明"。
> 配套：`docs/技术文档.md`（完整数据与归因）、`docs/DEPLOY.md`（部署与排障）、`docs/PATCH_TCM.md`（TCM 改造）。

## 0. 图片分两类（先看这一段，很重要）

| 类别 | 图 | 是什么 | 怎么来的 |
|---|---|---|---|
| **实机截屏** | 图 1 / 2 / 3 / 4 | K1 桌面上真实终端窗口的**像素级原始截图** | 在 K1 的 Wayland 会话（labwc + LXQt）里开 qterminal，接 tmux 会话，用 `tmux send-keys` 逐条敲入命令，命令真实执行完毕后用 `grim` 截取整屏。**截取后的唯一处理是裁掉窗口下方空白行和等比缩放**，没有改任何像素内容；每张图右侧的「指标卡」是排版元素，画在截图区域之外。未裁剪的全屏原图（含桌面与任务栏）保存在 `docs/figs/demo/raw/figN_raw.png`，可随时核对 |
| **整理图** | 图 5 / 6 / 7 / 8 | 从 `results/` 归档的 llama-bench 记录**汇总**出的对照表 | **不是截屏**。标题栏已明确标注「整理图（非截屏）」。每张都写明数据来源文件与测量口径，数字可逐条回溯 |

**为什么图 5~8 不做截屏**：

1. 它们跨批次、跨模型（2B 官方与自产是两次独立 bench；长上下文四档分别耗时 1~30 分钟），任何单次截屏都放不下；
2. 本机运行时 `llama-bench`（0.1.1）**不接受多个 `-m`**（传两个会报 `failed to load model`），
   只能一个模型跑一次；单模型 `-p 64,512 -n 128 -r 3` 约 3~6 分钟，两轮连跑后终端还要滚动查看，
   一张 1920×1080 的整屏放不下两张完整表；
3. 所以性能对比以「带来源文件与测量口径的整理表」呈现，原始数据在 `results/*.txt`（纯文本，可直接核对）。

把整理表做成带来源标注的表格，比拼凑一张"看起来像终端"的图更诚实——这也是图 5~8 标题栏写「整理图（非截屏）」的原因。

**复核方法**：

```bash
# 在 K1 上重跑图 1~4 的命令（见 §1 总表），应得到同样的输出
# 查图 5~8 的原始记录
ls ~/cie/results/          # bench_2b_*.txt / bench_4b_*.txt / bench_depth_self.txt
```

## 2. 逐图说明

### 图 1 · 环境与硬件身份（实机截屏）

- **画面要点**：`riscv64` 出现在内核串里；ISA 串里 `_zve32x/_zve64d/_zvfh`（RVV）与结尾 `_ime` 同时存在。
- **标注**：8 核、7849 MB（可用约 7 GB）、Bianbu 2.3.5、Linux 6.6.63、NVMe 118 G。
- **图注**：*K1 实机：Bianbu 2.3.5 / 内核 6.6.63 / 8×X60，ISA 串中 RVV 与 IME 扩展同时在位——这是后续所有加速的前提。*

### 图 2 · 一键部署自检（实机截屏）

- **画面要点**：环境项逐条 `[OK]`；模型体积；冒烟 `推理正常出字` 与末尾 `通过 14 项，失败 0 项`。
  （该截屏摄于 `docs/hashes.txt` 加入之前；现在同一脚本会多跑一项 sha256 校验，结果为 15 项。）
- **标注**：14/14（环境 11 + 模型 2 + 冒烟 1；加哈希清单后为 15）、2B 1265 MB、4B 2573 MB、冒烟 3.1 t/s。
- **图注**：*`deploy.sh` 从架构、扩展、内存、依赖包一路检到模型体积与冒烟推理，14 项全绿；脚本失败即停并给出修复建议。*

### 图 3 · 根因：量化类型是否在 IME 白名单内（实机截屏）

- **画面要点**：两份"类型分布"行；官方那份含 `Q5_K / Q8_0 / Q6_K`，自产那份只有 `Q4_0`（外加 1 个 `Q8_0` 的 embedding）。
- **标注**：非白名单张量 **55 → 1**（Q5_K 18 + Q8_0 36 + Q6_K 1）；Q4_0 张量 129 → 186；体积 1.12 → 1.22 GiB。
- **图注**：*文件名都叫 Q4_0，实际类型分布完全不同：官方文件混入 55 个不在 IME 白名单的张量，整条 prefill 通路退化为通用实现。*
- **答辩提示**：这张图是"为什么快"的唯一解释，先看它再看性能表，因果链才闭合。

### 图 4 · 端到端出字（实机截屏）

- **画面要点**：模型对中文提问的实际回复文本，无乱码、无重复。
- **标注**：2B 生成 2.8 t/s（`-n 260` 长输出实测，与 bench 的 2.80 一致）、4B 1.4 t/s（与 bench 的 1.43 一致）。
- **图注**：*同一台机器上的中文生成：词表、chat 模板、MTP 剥离后的张量布局全部正确。*
- **说明**：该模型默认开启思考模式（`--chat-template-kwargs '{"enable_thinking":false}'` 与 `/no_think` 在本版运行时均未生效），
  截图里的思考过程是模型真实输出的一部分；回复末尾的表情符号在终端字体里显示为方框，属正常渲染。

### 图 5 / 图 6 · 官方 vs 自产（2B / 4B）（整理图）

- **画面要点**：三行配置（官方 Q4_0 / 自产 Q4_0 / 自产 Q4_K_M）+ 条形图。
- **标注**：2B `pp512 10.84 → 20.36（+87.8%）`，decode `2.84 → 2.80`；4B `3.80 → 8.10（+113.2%）`，decode `1.32 → 1.43（+8.3%）`。
- **图注**：*同硬件、同运行时、同参数，只换权重文件：2B prefill 翻倍、4B prefill 翻倍且 decode 转正。decode 在 2B 上几乎不变，说明它受带宽约束，与量化类型无关。*
- **答辩提示**：被问"是不是调参调出来的"时，指这一行——变量只有量化类型一个。

### 图 7 · 长上下文下的优势保持（整理图）

- **画面要点**：0 / 4096 / 8192 / 16384 四档深度，两版 pp512 与 tg64 成对出现。
- **标注**：`20.24 / 14.65 / 11.76 / 8.26`；优势 `+87.8% / +62.8% / +51.7% / +37.4%`；decode 保持率 `44.8% vs 45.8%`。
- **图注**：*优势随深度单调收窄但始终为正；decode 两版衰减曲线几乎重合——上下文衰减由注意力通路决定，与权重量化无关。*

### 图 8 · 负结果排除矩阵（整理图）

- **画面要点**：四条被排除的路径及其实测数字、判定列。
- **标注**：v0.2.3 `7.99`（比 legacy 低 23%）；`-t 8` → `0.86`（−70%）；TCM patch `20.36 → 20.36`（Δ0）；KV q8_0 `31 min 未完成`（f16 仅 17.9 min）。
- **图注**：*四条直觉路径全部被实测排除，优化点因此收敛到单一变量：量化类型。*

### 附 A · 2B 官方与自产的单次实跑（实机截屏）

- **画面要点**：同一终端里连跑两个模型，两张 `llama-bench` 表上下排列，各自带 `build: 17ce6aa (1)`。
- **标注**：官方 pp64/pp512/tg128 = 11.27 / **10.85** / 2.84；自产 = 20.18 / **20.04** / 2.79；本次提升 **+84.7%**。
- **图注**：*独立复跑（-r 2）得到 +84.7%，与 §8.1 的 +87.8% 差 1.7%，落在文档自述的 ±2.6% 重复性范围内：结论稳定，绝对值随批次小幅浮动。*
- **作用**：给图 5 的整理表配一张**未经编辑的原始证据**；同时它也是"官方 10.84 可复现"的直接证据（本次 10.85）。

## 3. 如何重新截一张真图（可复现流程）

```bash
# 1) 在 K1 上（不是 ssh 里）：开一个终端，接 tmux
tmux new -s demo

# 2) 把 §1 总表第 3 列的命令逐条敲进去，等它跑完

# 3) 整屏取证（K1 本机执行；Bianbu 2.3.5 是 Wayland，不要用 x11grab）
grim shot.png            # 保存在当前目录
```

> 提示：Bianbu 2.3.5 的桌面是 Wayland（labwc 合成器），`ffmpeg -f x11grab` 抓到的是空的 Xwayland 根窗口（全黑），
> 必须用 `grim`。本项目所有截屏均由 `grim` 产生。
